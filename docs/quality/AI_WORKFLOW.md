# AI 역할 및 작업 관리

사용자가 총괄 기획 및 승인자다. 하나의 모델에서 역할을 전환해도 되며, 복잡한 변경은 별도 검토 세션을 권장한다.

| 역할 | 작업 권한·담당 | 입력/산출물 |
| --- | --- | --- |
| 기획 | 읽기·분석·제안, 승인 전 구현 금지 | PROJECT_SPEC, 결정 기록 → 범위·수용 조건·보류 사항 |
| 개발 | 승인된 범위 구현 및 관련 테스트 | 작업 요청, 명세, 실제 코드 → diff·결과 |
| 코드 리뷰 | 독립적인 읽기 및 검토; 요청 전 코드 변경 금지 | diff·테스트·명세 → 파일/행, 재현·심각도·근거 |
| UI/UX | 디자인 기준과 실제 화면 비교 | 화면·카메라/디자인 기준 → 문제·개선안 |
| 에셋 QA | 수치 검사 및 기준 이미지 대조 | PNG·프로필·원본 → 통과/실패/판단불가 |
| 기능 QA | 테스트 작성/실행, 운영 데이터 접근 금지 | 테스트 계획·diff → 실제 결과·미검증 |
| 마케팅 분석 | 집계 데이터 분석, 기획 제안만 | 익명 집계 통계 → 기간·분모·지표·개선 가설 |

## 작업 흐름
1. 요청, 관련 기준서·코드, 현재 변경사항을 확인한다.
2. 기획 변경이면 사전 승인. 승인된 범위의 일반 구현이면 진행한다.
3. 구현 뒤 관련 회귀 테스트를 실행. 고위험 변경은 별도 리뷰 세션에서 다시 검토한다.
4. 실패 원인을 고치고 재실행. 시각 판단과 실제 브라우저 검증은 별도로 표시한다.
5. 변경 파일·결과·미검증 사항·배포 상태를 인계한다. main 병합 및 운영 반영은 승인 단계다.

## 작업 요청 양식
```text
[역할] 기획 / 개발 / 코드 리뷰 / UI·UX / 에셋 QA / 기능 QA / 마케팅
[작업] 원하는 한 가지 결과
[범위] 대상 기능·화면·파일 (모르면 기존 코드에서 식별)
[보존] 유지해야 할 기존 동작·디자인
[수용 조건] 실제로 검증 가능한 완료 기준
[출력] 변경/근거/검증/미검증/배포 상태
```

짧은 요청도 허용한다. AI가 관련 역할과 기준 문서를 식별하며, 중요하게 달라지는 판단만 사용자에게 확인한다.

## 문서 관리
- 사실의 출처를 한 곳으로 유지: 구현 상태는 README/코드, 아트 규격은 기존 픽셀 기준서, 좌표는 카메라 기준서에 둔다.
- 새 기획은 DRAFT → REVIEW → APPROVED로 전환하고, 실제 검증 뒤 IMPLEMENTED로 기록한다. 폐기는 DEPRECATED.
- 제안과 취소된 규칙을 자동 적용하지 않는다. 결정 변경 시 DECISIONS에 날짜·근거·영향·승인·검증을 기록한다.
- 충돌하면 최신 명시적 사용자 승인과 관련 기준서를 우선 확인한다. 불명확하면 멈추고 질문한다.
